1. VISIÓN GENERAL DEL PROYECTO
================================================================================

TIENDAPP es un Sistema POS (Point of Sale) SaaS especializado en:
  • Gestión de ventas para pequeños negocios
  • Control de inventario en tiempo real
  • Multi-tenant (múltiples tiendas independientes)
  • Autenticación con JWT y roles (admin/tendero)
  • Reportes en Excel

STACK ACTUAL:
  Backend:  FastAPI 0.104.1 + SQLAlchemy 2.0 + PostgreSQL 14
  Frontend: React 19.2.5 + Vite 8.0.10 + Tailwind CSS 4.2.4
  
USUARIOS ACTIVOS:
  • Administradores: Crean productos, ven reportes
  • Tenderos: Registran ventas, ven historial

3. LÓGICA DE NEGOCIO - FLUJO CRÍTICO (Venta)
================================================================================

PASO 1: Usuario selecciona productos en vitrina
        └─ Se agregan a estado "cart" en memoria (React)

PASO 2: Usuario hace click en "COBRAR"
        └─ Frontend envía: POST /ventas/{empresa_id}
           Body: { detalles: [{producto_id, cantidad}] }

PASO 3: Backend valida y crea transacción ACID
        ├─ Valida JWT token
        ├─ Valida empresa_id del usuario
        ├─ Crea registro Venta (total = 0 inicialmente)
        ├─ PARA CADA DETALLE:
        │  ├─ Bloquea fila de Producto con .with_for_update()
        │  ├─ Valida: cantidad_actual >= solicitado
        │  ├─ Descuenta: producto.cantidad_actual -= cantidad
        │  ├─ Calcula: subtotal = precio * cantidad
        │  └─ Crea DetalleVenta (precio congelado)
        ├─ Actualiza: venta.total = suma de subtotales
        └─ db.commit() o db.rollback() (TODO O NADA)

PASO 4: Respuesta al cliente
        ├─ ✅ Si success: carrito se vacía, inventario recarga
        └─ ❌ Si error: se revierte TODO (rollback ACID)

4. ERRORES IDENTIFICADOS Y SOLUCIONES
================================================================================

ERROR 400 - BAD REQUEST:
├─ "Stock insuficiente"
│  └─ CAUSA: Sin bloqueo de fila (race condition)
│     SOLUCIÓN: .with_for_update() antes de validar

├─ "Producto no encontrado"
│  └─ CAUSA: No valida empresa_id del producto
│     SOLUCIÓN: Query con ambas condiciones (id AND empresa_id)

├─ "Este email ya está registrado"
│  └─ CAUSA: No pre-valida duplicidad
│     SOLUCIÓN: .first() antes de crear usuario

└─ "Código de barras duplicado"
   └─ CAUSA: No valida único a nivel aplicación
      SOLUCIÓN: Pre-validar en /productos/

ERROR 405 - METHOD NOT ALLOWED:
├─ POST a endpoint GET-only
│  └─ CAUSA: Confusión entre métodos HTTP
│     SOLUCIÓN: Documentar claramente POST vs GET

├─ Endpoint duplicado
│  └─ CAUSA: /ventas/{empresa_id} definido 2 veces (líneas 399 y 492)
│     SOLUCIÓN: Eliminar duplicado, mantener versión con dependencies

└─ CORS no configurado
   └─ CAUSA: OPTIONS request devuelve 405
      SOLUCIÓN: CORSMiddleware en FastAPI

5. FORTALEZAS A MANTENER
================================================================================

✅ MULTI-TENANT BIEN DISEÑADO
   - Cada usuario solo ve su empresa_id
   - Imposible ver datos de otro negocio
   - Escalable a cientos de tiendas

✅ SEGURIDAD SÓLIDA
   - JWT con OAuth2PasswordBearer
   - Contraseñas hasheadas con bcrypt
   - Roles definidos (admin vs tendero)
   - CORS configurado

✅ TRANSACCIONES ATÓMICAS
   - with_for_update() previene race conditions
   - db.commit() o db.rollback() (TODO O NADA)
   - Integridad de stock garantizada

✅ SEPARACIÓN CLARA
   - Backend + Frontend desacoplados
   - API REST bien definida
   - Validaciones en 2 capas (Backend + Frontend)

✅ USADO EN PRODUCCIÓN
   - Maneja múltiples tiendas reales
   - Datos históricos en BD
   - Usuarios activos usando el sistema

6. PROBLEMAS A RESOLVER
================================================================================

⚠️ DUPLICIDAD DE CÓDIGO
   - Esquemas Pydantic repetidos 3 veces en main.py
   - Deberían estar en app/schemas/

⚠️ PROPS DRILLING EN REACT
   - 8 props pasados por 5 niveles
   - Solución: Context API

⚠️ FALTA DE LOGGING
   - No hay trazabilidad de operaciones
   - Difícil debuggear en producción

⚠️ SIN TESTS
   - 0% coverage
   - Cambios futuros son riesgosos

⚠️ FALTA DE AUDITORÍA
   - No se sabe quién creó/modificó cada registro
   - Falta: created_by, updated_by, deleted_at

⚠️ VERSIONADO DE API
   - No hay /v1/, /v2/
   - Cambios futuros romperán clientes
